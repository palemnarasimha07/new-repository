01 Project Overview

1.1 Project Title & Core Purpose

The NCC Digital Cadet System is a cloud-native, full-stack enterprise web portal engineered to modernize, streamline, and digitize the operational lifecycle of the National Cadet Corps (NCC) across India. It serves as an integrated command, administration, and evaluation platform uniting three distinct user categories: Cadets, Associate NCC Officers (ANOs) / Unit Instructors, and Commanding Officers (COs) / Battalion Administrators.

1.2 Problem Statement

Historically, NCC battalion and sub-unit management relies on physical ledgers, paper muster rolls, manual examination tabulation, and offline certificate distribution. This legacy paradigm suffers from severe institutional bottlenecks:

  • Dispersed Paper Records: Drill sessions, physical training hours, and camp muster rolls (e.g. CATC, NIC, RDC) are logged on handwritten physical registers susceptible to moisture damage, ink decay, and catastrophic physical loss.
  • Opaque Exam Preparedness: Cadets preparing for mandatory 'A', 'B', and 'C' Certificate examinations have no transparent means to calculate their qualification eligibility (such as mandatory 75% parade attendance and camp requirements).
  • Absence of Standardized Testing: Sub-units lack automated question banks, standardized difficulty rating engines, and computerized examination tools for defense syllabus subjects.
  • Credential Forgery Vulnerability: Physical paper NCC certificates are vulnerable to unauthorized modification or reproduction, placing high manual verification workloads on universities, employers, and Services Selection Boards (SSB).

1.3 Objectives

  • End-to-End Lifecycle Digitization: Manage enrollment, demographic records, biometric/parade attendance, training schedules, examinations, and achievements in a unified cloud interface.
  • Algorithmic Readiness Intelligence: Implement an automated, multi-factor Mathematical Readiness Engine that calculates an objective eligibility index (0–100%) for certificate examinations based on statutory attendance and camp completions.
  • Objective Assessment & Analytics: Provide topic-categorized MCQ pools with difficulty classification (Easy, Medium, Hard), timer-enforced online mock tests, and batch performance analytics.
  • Cryptographic & QR-Based Verification: Provide an open, zero-authentication public certificate verification portal (/verify-certificate/:certNo) allowing instant authentication via dynamic QR codes.
  • Role-Based Administrative Accountability: Ensure strict separation of duties between Cadets, Officers, and Admins enforced via signed JSON Web Tokens (JWT) and immutable audit logging.

02 Complete Features and Functionalities

Every feature documented below represents verified, existing source code within the project.

2.1 Authentication & Role-Based Access Control

Feature: Multi-Portal Login & Session Management

Purpose: Provide secure, role-segregated entry points for Cadets, Officers, and Administrators with session persistence.

Access: All registered users.

How it works: The login UI (Login.jsx) provides three role tabs (Cadet, ANO/Officer, CO/Admin). Submitting credentials issues a signed JWT token on the backend or validates against localStorage (findCadetUser in AuthContext.jsx). Successful login hydrates user state and redirects to role-specific dashboard (/cadet/dashboard, /officer/dashboard, or /admin/dashboard).

Frontend Implementation: frontend/src/pages/Login.jsx, frontend/src/context/AuthContext.jsx.

Backend Implementation: POST /api/v1/auth/login in backend/server.js with bcrypt.compareSync and jwt.sign.

Database/Store: Validates against usersDB array (backend) and nccCadets / STATIC_USERS (client state).

Feature: Forced First-Time Password Change & Officer Password Reset

Purpose: Enforce security hygiene by requiring cadets to set a secure password upon initial login and allow officers to reset forgotten passwords.

Access: Cadets (self-change), Officers/Admins (reset cadet passwords).

How it works: If a cadet record has mustChangePassword === true, the modal ForcePasswordChangeModal.jsx intercepts navigation until a new password (min 4 characters) is submitted. Officers can trigger resetCadetPassword(cadetId) in CadetManagement.jsx, which resets the credential to default and re-arms the forced-change flag.

Frontend Implementation: ForcePasswordChangeModal.jsx, AuthContext.jsx (changeCadetPassword, resetCadetPassword).

Backend Implementation: POST /api/v1/auth/reset-password with token verification.

Database/Store: Updates password and mustChangePassword in nccCadets localStorage and usersDB.

2.2 Cadet Portal Modules

Feature: Cadet Dashboard & Dynamic Readiness Dial

Purpose: Provide enrolled cadets a central mission-control screen showing personal metrics, attendance dials, upcoming exams, urgent announcements, and eligibility gap-analysis.

Frontend Implementation: frontend/src/pages/cadet/CadetDashboard.jsx, components/CadetReadinessCard.jsx.

Storage: Pulls from nccTrainings, nccExams, nccAnnouncements, nccAchievements, and nccResults_${userId}.

Feature: Algorithmic Cadet Readiness Index Engine

Purpose: Mathematically calculate a transparent, objective 0–100% exam readiness score for certificate board examinations.

Access: Cadets (self view), Officers (batch view via modals).

How it works: Executes calculateCadetReadiness() in readinessCalculator.js with configurable weights: Attendance (20%), Training Completion (25%), Examination Marks (25%), Physical & Drill (15%), and Achievements & Camps (15%). Returns an overall score, category breakdown, status tier ("Outstanding Readiness", "Satisfactory Readiness", "Needs Improvement / At Risk"), and color codes.

Implementation: frontend/src/services/readinessCalculator.js.

Feature: Computer-Based Testing (CBT) & Timed Mock Exam Engine

Purpose: Allow cadets to take timer-enforced online exams with anti-cheating warnings, immediate grading, and question-by-question review.

Access: Role: cadet.

How it works: Loads published exams from nccExams. When started, a countdown timer (Timer component) begins. Cadets select MCQ options (A, B, C, D). Includes proctoring simulation UI (webcam placeholder, full-screen prompt, tab-switch warning count). Upon submit or timer expiry, computes marks, percentage, pass/fail status, saves response payload into nccResults_${userId}, and launches AnswerReview showing correct answers and explanations.

Frontend Implementation: frontend/src/pages/cadet/CadetExams.jsx.

Purpose: Analyze historical exam mistakes to identify weak knowledge topics and suggest corrective study actions.

Access: Role: cadet.

How it works: recommendationEngine.js parses per-question topic answers across past tests. Topics scoring below 65% are flagged as Weak Topic, generating targeted study cards (e.g. Map Reading, First Aid) and remedial recommendations.

Frontend Implementation: frontend/src/services/recommendationEngine.js, invoked in CadetDashboard.jsx.

Feature: Cadet Profile, Attendance History, Achievements & Certificates

Purpose: Complete self-service digital portfolio for cadets.

Access: Role: cadet.

How it works:

  • CadetProfile.jsx: Digital ID Card with QR code, regiment number, wing, blood group, institution, and contact info.

3.3 State Management & Data Hydration

State is managed through a hybrid architecture:

  • Authentication Context (AuthContext.jsx): Global React Context providing user, login, logout, changeCadetPassword, and role booleans (isCadet, isOfficer, isAdmin).
  • Browser LocalStorage Persistence: seedData.js runs on initialization, populating default schemas for cadets, trainings, exams, announcements, and certificates. Component state synchronizes changes to localStorage on mutations.
  • REST API Fallback Architecture (api.js): apiRequest() attempts communication with Express backend endpoints (/api/v1/*). If the backend is offline (such as in an offline evaluation demo), it gracefully falls back to local storage without throwing unhandled exceptions.

4.2 Middleware Architecture

The backend incorporates modular middleware defined in backend/middleware/auth.js:

  • authenticateToken(req, res, next): Extracts the bearer token from the Authorization: Bearer <token> header. Verifies signature using JWT_SECRET. Rejects invalid or expired tokens with HTTP 401/403. Attaches decoded token payload (req.user) to the request object.
  • authorizeRoles(...roles): Higher-order authorization guard. Checks whether req.user.role matches allowed roles for the requested endpoint. Returns HTTP 403 Forbidden on role mismatch.
  • express.json(): Parses incoming JSON request payloads up to standard body size limits.
  • Unified SPA Static Serving Middleware: Custom middleware in server.js (lines 107–135) that inspects incoming requests. If the request does not start with /api/, it dynamically checks if frontend/dist exists and serves static assets, falling back to dist/index.html for client-side HTML5 pushState routing.

09 Security Implementation

9.1 Actually Implemented Security Controls

  • Cryptographic Password Hashing: Passwords in backend stores are processed with bcryptjs using 8 salt rounds, preventing plaintext credential leakage.
  • Stateless JWT Token Issuance: Tokens signed with HMAC-SHA256 (HS256) using server-side secret JWT_SECRET, configured with a 12-hour expiration window.
  • Role-Based Access Control (RBAC): Route-level middleware (authorizeRoles("admin")) and React Router protection wrappers (ProtectedRoute) strictly segregate access boundaries between Cadets, Officers, and Admins.
  • Forced Password Hygiene: Cadets initialized with default phone credentials are compelled to establish custom passwords on first login via mustChangePassword gating.
  • CORS Whitelisting: Cross-Origin Resource Sharing is controlled in Express via the ALLOWED_ORIGINS environment configuration.
  • Security Audit Logging: Sensitive events (logins, password modifications, exam publishing) generate structured audit entries recorded with actor identities and timestamps.

9.2 Known Security Limitations & Missing Controls

Identified Production Security Deficits (To Address in Next Release):
  1. Rate Limiting Missing: No request throttling (e.g. express-rate-limit) exists on /api/v1/auth/login, rendering the endpoint susceptible to brute-force attacks.
  2. Missing HTTP Security Headers: The application does not integrate helmet to set Content Security Policy (CSP), Strict-Transport-Security (HSTS), or X-Frame-Options headers.
  3. Client-Side Demo State Vulnerability: Sensitive cadet data stored in browser localStorage is unencrypted and accessible via DevTools or Cross-Site Scripting (XSS).
  4. Ephemeral Backend Store: In-memory user credentials and audit logs are reset whenever the container restarts.

11 Deployment Architecture

11.1 Multi-Stage Production Dockerfile

The project is containerized using a clean two-stage Docker architecture defined in Dockerfile: 

# Stage 1: Build React Frontend SPA
FROM node:20-alpine AS frontend-builder
WORKDIR /app/frontend
COPY frontend/package*.json ./
RUN npm ci
COPY frontend/ ./
RUN npm run build

# Stage 2: Express Backend + Static Assets Runner
FROM node:20-alpine AS runner
ENV NODE_ENV=production
ENV PORT=8080
WORKDIR /app/backend
COPY backend/package*.json ./
RUN npm ci --only=production
COPY backend/ ./
COPY --from=frontend-builder /app/frontend/dist /app/frontend/dist
EXPOSE 8080
CMD ["node", "server.js"]
